# Vault2077 OPC 服务目录后台操作手册

## 1. 这套后台管理什么

OPC 后台管理面向用户的人工服务内容，并处理公开服务订单：

- 基础设施；
- 专项服务；
- 游骑兵协会公开档案。
- OPC 标准服务订单的付款核验、完成、取消与退款状态。

资讯、来源、SiC 内容与榜单、Frontier 排名不在这里编辑。OPC 后台也不是通用页面搭建器：三个一级入口、三个基础设施浏览分组、六个专项领域和十类游骑兵身份由设计规格控制，不能在后台任意新增分类。

## 2. 本地进入后台

1. 在项目目录运行 `npm run dev`。
2. 浏览器打开 `http://127.0.0.1:3000/admin`。
3. 输入本地开发密码并登录。
4. 在后台顶部功能导航选择“OPC 菜单”维护目录；选择“OPC 订单”处理付款与交付状态。

本地开发环境如果没有配置后台密码，当前代码使用开发专用默认密码 `vault2077-local-admin`。也可以通过环境变量 `VAULT2077_ADMIN_PASSWORD` 设置本地明文密码。该适配器只允许本地开发，在 `NODE_ENV=production` 下关闭。

生产环境从独立管理域名进入，应用要求唯一 `owner` 使用绑定该域名的原生 Passkey 完成设备用户验证后建立会话；不显示共享密码登录。后台应用会话在连续 30 分钟无操作后失效，最长持续 4 小时，并可由服务端单独撤销。

## 3. 认识服务目录界面

页面右上角显示三个状态：

| 状态 | 含义 |
| --- | --- |
| `REVISION` | 当前目录修订号；每次保存草稿或发布都会增加 |
| `DRAFT` | 最近一次保存草稿的时间 |
| `PUBLISHED` | 最近一次成功发布公开目录的时间 |

目录分为三个页签：

| 页签 | 可管理内容 |
| --- | --- |
| 基础设施 | 完整经营能力项目 |
| 专项服务 | 固定范围、固定成果的单项服务 |
| 游骑兵协会 | 外部独立顾问的授权公开档案 |

页签数字是当前草稿中的项目数量。选择页签后，左侧是项目列表，右侧是当前项目的编辑表单。

## 4. 编辑现有服务

1. 选择“基础设施”或“专项服务”。
2. 在左侧选择要修改的服务。
3. 在右侧修改字段。
4. 列表型字段按“一行一项”填写；保存时会忽略空行并去除重复项。
5. 点击“保存草稿”，确认后写入服务器草稿。
6. 完成整份目录的公开内容确认后，点击“校验并发布”；生产环境若最近 5 分钟没有重新验证身份，会要求再次使用 Passkey。

服务字段包括：

- 稳定路径 `slug`；
- 服务编号和名称；
- 基础设施浏览分组，或专项服务所属领域；
- 一句话结果和适用对象；
- 包含内容、交付成果、所需材料；
- 超出范围与转交边界；
- 公开价格或计价单位、标准周期；
- 修订编号、公开状态。

`slug` 只能使用小写字母、数字和连字符。服务发布后不建议修改 `slug`，否则旧链接无法恢复原来的选中项。

## 5. 编辑游骑兵档案

1. 选择“游骑兵协会”。
2. 在左侧选择顾问档案。
3. 先确认稳定 `slug`，再选择本人授权公开的 PNG、JPEG 或 WEBP 头像；文件最大 5MB，宽高均不得小于 320px。
4. 上传接口立即在服务端去除元数据、裁剪并生成 320×320 与 800×800 两份 WebP；后台不接受任意第三方图片 URL。
5. 修改公开名称、主要身份、介绍、专长标签、公开资质或职业记录。
6. 只有取得本人授权后，才能填写并发布公开联系方式和头像。
7. 填写核验日期、资料更新时间和本人授权状态。
8. 保存草稿；头像上传成功只会更新当前浏览器草稿，仍需保存草稿或发布才能写入目录引用。

游骑兵档案发布后会同时影响 OPC 工作台的肖像墙、游骑兵目录和个人公开档案页。

本地开发把处理后的头像保存在 `data/ranger-media/` 并通过 `/media/*` 访问。生产环境必须使用 `VAULT2077_RANGER_MEDIA_STORAGE=oss` 和独立媒体域名；目录发布前会检查两份对象存在且哈希元数据一致。替换或移除头像只改变目录引用，不会立即删除旧对象；每天运行 `npm run opc:cleanup-ranger-media` 清理超过保留期且无活跃引用的对象。本人撤回授权时，先从草稿和公开目录移除头像并发布，再运行 `npm run opc:purge-revoked-ranger-media -- <ranger-slug>` 枚举并删除该专家的当前对象、全部历史 versionId 和删除标记，同时记录人工操作审计。正式运营前必须在真实 OSS 完成这两条命令、定时任务和版本化永久删除验收。

## 6. 新增、排序和删除

- “新增项目”：在当前页签末尾加入一个草稿项目。
- “上移 / 下移”：调整项目在当前页签内的公开顺序。
- “从草稿移除”：只从当前草稿删除；公开页面暂时不变。
- “放弃本地修改”：重新读取服务器草稿，丢弃本次尚未保存的浏览器表单修改。

新增项目后必须先检查自动生成的 `slug`、编号和分类，再补齐所有公开字段。

删除、排序和新增都要经过“保存草稿”或“校验并发布”。只有成功发布后，公开目录才发生变化。

## 7. 保存草稿与发布的区别

| 操作 | 写入服务器 | 影响 OPC 前台 | 产生审计记录 |
| --- | --- | --- | --- |
| 只在表单中输入 | 否 | 否 | 否 |
| 保存草稿 | 是 | 否 | 是 |
| 校验并发布 | 是 | 成功后影响下一次页面请求 | 是 |

发布不是逐条发布，而是用当前草稿整体替换公开目录。只要目录中的任何项目未通过发布检查，整次发布都会失败，上一公开版本继续生效。

成功发布后：

- 新打开 OPC 页面会立即读取新版本；
- 已经打开的 OPC 页面不会自动推送更新，需要刷新页面或重新进入；
- 本地开发不需要重新启动开发服务器；
- 不需要重新构建项目。

## 8. 处理 OPC 订单

纸质签约订单在用户确认并可下载完整的在线订单及预付款协议后创建，保存当时的服务、价格、协议标题、完整正文、版本、SHA-256、签约方式和确认时间快照。目录、价格或协议之后修改不会改写历史订单。运行时代码已经实现；真实付款入口仍由生产门禁控制，只有支付宝生产资料、邮件发送、数据库、定时任务和真实交易演练全部通过后才可开放。

1. 打开“OPC 订单”，核对订单号、服务、应付金额、在线协议版本、支付渠道和创建时间；默认只显示遮罩后的联系人与寄送地址。
2. 正常付款由支付宝验真异步通知或主动查询更新为“已付款待合同确认”。浏览器返回页、付款截图和口头说明都不是到账依据。
   首次确认到账时，系统生成唯一付款凭证和 outbox 事件；独立定时任务在回调之外向 `lanzhouda@163.com` 投递仅含订单摘要和独立管理域名链接的邮件。邮件失败不改变到账状态，定时任务按退避策略使用同一 Message-ID 重试并以非零退出触发告警；普通 SMTP 的投递语义为 at-least-once。
3. 若用户反馈已付款但订单仍为待付款，选择“查询支付宝状态”。该操作要求最近五分钟再认证；系统使用订单绑定的 APPID 发起签名查询，并核对查询返回的订单号、金额以及下单时绑定的商户 PID。
4. 线下合同处理由运营方自行完成，后台不创建寄件、返寄、催办或纸质核验任务。运营方得到结论后，只选择“合同门禁通过”或“发起全额退款”。
5. “合同门禁通过”把订单推进为可履约状态；必须二次确认、检查预期版本并留下不可变审计。
6. “发起全额退款”使用原支付交易、服务器保存金额和稳定退款请求号；订单先进入“退款处理中”。重试时先查询同一退款请求，只有支付宝明确返回不存在才重新提交，避免重复退款。只有支付宝退款结果确认成功后才显示“已全额退款”，不得扣除打印、寄送或其他费用，也不得人工跳过退款核验。
7. 服务完成只允许从可履约状态进入“已完成”；未付款订单可以关闭，已付款订单不能直接取消。

订单详情采用一个贯通 dossier：服务与完整在线协议快照、签约主体、遮罩联系人和地址、支付宝交易、付款凭证、合同门禁、退款和审计轨迹在同一页面查看。管理员可以下载与用户同源的凭证数据；查看完整联系人或寄送地址需要最近五分钟再认证并单独审计。付款凭证显示我方名称、统一社会信用代码、用户签约主体、服务、金额、规范网址、当前订单状态和 ICP 备案号，并明确不替代发票。

线上状态为 `待付款 → 已付款待合同确认 → 已到账可履约 → 已完成`，退款分支为 `已付款待合同确认/已到账可履约 → 退款处理中 → 已全额退款`。任何身份、订单号、金额或状态不一致的真实到账进入异常核对，不能正常交付。

订单联系人和寄送地址只用于纸质签约、付款/退款、联系和交付，不得复制到内容管线、公开页面、分析事件或非受控表格。读取完整值要求最近五分钟再认证并审计。未付款取消订单满 90 天清除地址和联系人；已付款订单完成或退款满 24 个月后清除非合同联系方式和地址。

## 10. 发布检查

服务发布至少要求：

- `slug`、编号、名称完整且不重复；
- `slug` 格式有效；
- 分组或专业领域属于受控分类；
- 一句话结果、适用对象、转交边界完整；
- 包含内容、交付成果、所需材料各至少一项；
- 价格、周期、修订和公开状态已填写且不是占位值。

游骑兵发布至少要求：

- `slug`、公开名称、介绍和身份完整；
- 至少一个专长标签；
- 本人授权的公开联系方式和联系状态有效；
- 核验日期、资料更新时间和授权状态完整且不是占位值。
- 如设置头像，两份托管媒体对象均存在且哈希元数据一致。

如果另一后台会话先保存或发布，当前页面的旧修订号会触发版本冲突。此时先复制尚未提交的重要文字，再刷新后台并基于最新草稿重新修改；系统不会用后到请求静默覆盖先前修改。

## 11. 本地数据保存在哪里

未配置 PostgreSQL 时，本地开发使用文件预览存储：

`data/opc-service-catalog.json`

订单保存在：

`data/opc-orders.json`

该文件已被 Git 忽略。正常重启开发服务器不会丢失内容。不要在后台运行期间手工修改这个 JSON 文件。

本地后台每次成功“校验并发布”后，还会将已发布目录同步到受 Git 跟踪的默认 seed：

`data/defaults/opc-catalog.seed.json`

seed 只包含已发布目录和来源修订信息，不包含草稿、管理员会话、审计日志或完整发布历史。seed 写入失败时，本地发布请求也会失败，避免后台显示发布成功但默认内容未更新。可使用 `npm run opc:sync-seed` 手工重新导出当前已发布内容。

这一自动同步只在未配置 PostgreSQL 的标准本地开发模式启用。生产环境和 PostgreSQL 模式不会尝试修改部署包中的 seed。

生产环境配置 PostgreSQL 后，目录和订单分别保存在 `vault2077_state_documents` 表的 `opc-service-catalog` 与 `opc-orders` 状态文档中。每次成功发布都会保留完整目录快照，但当前后台尚未提供一键回滚界面。

管理员不需要 SSH 登录服务器，也不修改生产 JSON。外部浏览器通过受保护管理域名编辑，后台接口把内容写入 PostgreSQL；发布成功后，公开 OPC 页面下一次刷新读取新快照。

## 12. 推荐操作顺序

1. 进入后台并确认 `REVISION`、`DRAFT`、`PUBLISHED`。
2. 先在草稿中完成一批内容修改。
3. 保存草稿。
4. 展开发布前检查，逐项清除错误。
5. 由相应专业负责人确认价格、范围、材料、周期、成果和专业责任。
6. 再次检查项目排序和公开联系方式。
7. 点击“校验并发布”并确认。
8. 新开一个 `/opc` 页面检查工作台、分类页和游骑兵档案。
9. 发现问题时继续建立新草稿修订，不直接手改存储文件。

普通文案、价格、服务项目和顾问档案变更通过后台完成即可，不需要修改项目设计文档。只有一级入口、受控分类、发布规则、责任边界或页面结构发生变化时，才需要先修订权威规格并同步实现。
