# Vault2077 OPC 服务台设计规格

## 1. 目标

OPC 把超级个体常见的经营支持分成两个清楚的责任边界：Vault2077 直接交付标准服务；外部独立顾问通过游骑兵协会展示并由用户直接联系。页面不得让用户误以为游骑兵由 Vault2077 雇用、定价或担保。

OPC 服务台标语固定为“超级个体，全栈运行”。标语和频道识别带之后的正式目录使用全站统一内容宽度，左右保留页面留白，但不得用四边细线把整个目录围成封闭盒子。目录三栏统一使用全站纸张底色，不得用彼此接近的灰白色制造局部组件岛；两条分栏细线从频道文字缎带下沿连续贯通至全站页脚上沿。窄屏改为纵向堆叠时，以贯穿内容宽度的横向细线表达相同结构。反色选中块不得停在无细线承接的版心边缘：第一栏左侧没有分栏线，因此其反色块必须从右侧分栏线一直延伸到浏览器视口左边缘；位于内部栏位的反色块则必须铺满相邻细线之间的完整宽度。任何反色块都不得成为四周留有缝隙的悬浮色块。

## 2. 三个一级入口

### 2.1 基础设施

基础设施是跨专业领域的完整标准交付。首版从完整需求池中优选以下七项高频、刚需且可标准化的经营底座：

1. 经营主体启动与首年治理
2. 财税与经营资金运行
3. 合同、交易与回款运行
4. 线上经营与平台准入
5. 用工与外部协作运行
6. 知识产权与数字资产运行
7. 数据、隐私与信息安全运行

名称表达经营能力，不按法律、财税等专业部门拆成一级导航。

七项是首版 SKU，不是永久不可变的数据库枚举。运营人员可以通过 OPC 菜单草稿增减、排序或修订具体项目；正式发布必须通过完整性校验。三个浏览分组“启动经营、上线与交付、持续安全运行”保持受控，避免后台演变为任意分类搭建器。完整需求池仍保留作后续版本研究，具体首版业务内容以 [OPC 服务清单](Vault2077-OPC-Service-Catalog.md) 为准。

### 2.2 专项服务

专项服务解决一个边界清楚的问题。首版优选十四项，并按六个面向 OPC 实际经营任务的专业领域辅助浏览：

- 法律与经营风险
- 财税与现金流
- 品牌与线上获客
- AI与企业数字化
- 用工与协作者
- 知识产权与产品商业化

专业领域只用于专项服务筛选，不替代“基础设施/专项服务”的一级结构。

### 2.3 游骑兵协会

游骑兵是外部独立顾问，按当前已发布的顾问身份浏览。初始兼容基线为：

- 法律顾问
- 财税顾问
- 知识产权顾问
- 创业顾问
- 产品顾问
- 品牌顾问
- 自媒体专家
- 设计师
- 软件工程顾问
- AI 开发专家

六个专业领域不套用到游骑兵；顾问可以使用专长标签补充能力，但只归属一个当前已发布的主要顾问身份。顾问身份使用稳定 ID 与可修改的公开名称，首次发布后稳定 ID 锁定，名称修改不得改变顾问归属；后台可以随同一份 OPC 草稿新增、改名、排序和删除空身份，仍被顾问引用的身份必须先完成迁移或移除。

工作台右侧的协会预览先显示面向用户问题与直接合作的常态文案，再接始终保持竖向的姓名书架，而不是头像网格或索引列表。文案按已有顾问入驻的长期状态书写，不暴露招募、准备、数据占位或鼠标操作说明。左侧身份导航按已发布 `rangerIdentities[]` 的顺序排列；右侧真实顾问书脊不与该导航逐项对齐或按身份重新分组，而是严格使用已发布目录 `rangers[]` 的顺序，使后台新增及“上移 / 下移”形成的公开顺序直接成为书脊顺序。真实顾问排完后，才按身份发布顺序补尚未入驻身份的空席。文案区与书架以一条横线分隔，书脊上沿紧贴该横线并自动伸展至右栏下边框，上下不得留白。每条书脊只写顾问公开名称，并将名称固定在书脊中部；鼠标悬停或键盘聚焦时以约 1.25 秒的舒展节奏在原位拉开，大头像以约 1.45 秒的稍缓动势完成，鼠标离开整座书架时以较短节奏收回。展开面由填满可用区域的大头像主导，只叠加主要顾问身份、公开名称和可选的个人签名，不显示简介、标签、编号、状态说明或独立按钮式详情入口；真实顾问的整张展开面是指向稳定 `/opc/rangers/[slug]` 的详情链接，键盘聚焦后也可进入，空席不产生链接。个人签名是顾问本人的一句话表达，最长 120 个字符，排在姓名下方且最多显示两行；未填写时整行不渲染，不生成占位文案。身份、姓名与签名直接署在头像上，不使用实心或半透明矩形底板；复杂和彩色头像的可读性由融入整幅画面的无边界底部渐隐与轻微文字阴影保证，不得重新形成独立卡片。书架按固定容量分页；宽屏将无边框、无底色的翻页三角固定在书架右侧页边留白，下一页朝右、返回朝左，不得覆盖书脊、展开头像或移入左侧导航；中间页同时需要前后翻页时，两枚三角只在右侧上下错开。窄屏页边留白不足时改为贴边的 2px 纯黑竖条。没有真实顾问的空席只写“待公开”，继续使用低对比模板肖像，不虚构姓名、联系方式、个人签名或授权状态。窄屏仍保持竖书脊构图，不重排为横向索引。

## 3. 标准服务合同

基础设施与专项服务均由 Vault2077 直接交付。每个服务修订必须包含：

- 名称与一句话结果；
- 服务类型和适用专业领域；
- 明确包含与不包含；
- 用户需提供的材料；
- 交付成果与交付形式；
- 可检查的验收标准；
- 标准周期；
- 固定价格或明确计价单位；
- 含税与第三方费用口径；
- 修订版本和公开状态。

每个公开服务详情提供无账号订单入口。用户确认服务名称、公开价格和范围后，选择自然人或法人/组织作为付款／委托方；法人/组织首期只支持法定代表人本人，不支持授权代理或内部审批链。当前唯一付款方式是线下对公转账；公开页面不展示已退役在线支付入口或恢复承诺。

线下付款页在转账前同页展示企业收款户名、开户银行、支行、账号和可选联行号，服务协议的查看弹窗与 PDF 下载入口，以及不带姓名、职务或介绍的联系人二维码。用户不必先转账再添加联系人，可以在转账前扫码沟通确认。提交表单要求签约联系人的真实姓名、有效中国大陆手机号、通过格式／日期／校验位检查的 18 位居民身份证号码和有效通知邮箱，只生成唯一订单号和同值付款附言，不自动扣款、不跳转第三方收银台，也不收集纸质合同寄送地址。该校验不表述为第三方实名认证。

用户必须在提交前完整查看并可下载服务订单及线下对公转账协议，主动确认服务快照、固定总价、真实企业收款主体和到账核验规则。服务协议确认与居民身份证号码的敏感个人信息单独同意使用两个独立复选框并分别留存版本／服务器时间。身份证号码字段加密，仅用于本订单签约主体核验和依法必要的合同留存，不用于营销、画像或无关事项；姓名、手机号和邮箱还用于订单履行、必要通知和退款联系。用户勾选并提交后订单协议成立；服务启动仍以企业银行实际到账核验和必要项目确认为条件。服务器保存服务、金额、协议正文/版本/SHA-256/确认时间、付款资料修订、企业账户快照、PDF 与二维码 SHA-256，以及加密付款方和联系人。后续替换公开资料不改变历史订单。

全站页脚提供 `/opc/refund` 退款申请入口。订单号只用于定位，服务器必须同时验证原订单恢复凭证；安全查询只显示订单号、服务、金额、付款方式和状态，不显示任何联系人、身份证或银行信息。已确认付款的订单可提交 10–800 字退款原因；原因加密且同一订单只能形成一份幂等申请和一个负责人 outbox。申请表示进入人工客服／财务核验，不改变付款或履约状态，也不表示退款已经批准或完成。

浏览器页面、截图、回单图片或用户声明不能改变到账状态。最近五分钟完成再认证的管理员必须按企业银行实际入账记录核对订单固定金额、付款户名、唯一银行流水号和入账时间；金额不一致、流水重复、订单版本陈旧或证据不完整时拒绝确认。付款户名加密保存，审计只保留流水指纹。订单创建事务同时写入面向用户和固定负责人的两个 `order_created` 通知事件；首次确认到账时冻结付款凭证，并分别写入面向用户和固定负责人的两个 `payment_confirmed` 通知事件。每个受众使用独立稳定 Message-ID 和重试状态，任一邮件失败不改变订单或到账事实。用户邮件只包含订单号、服务、金额、付款附言或到账摘要和公开状态入口；负责人邮件只包含脱敏摘要与独立管理域名 dossier 链接。邮件不得包含完整联系人、付款户名、企业银行账号、恢复凭证、二维码或即时通讯账号。

用户到账后可以查看和下载付款凭证图片。凭证列出服务快照、人民币实付金额、付款时间和银行流水号，我方名称与统一社会信用代码，用户委托主体资料和遮罩联系人；同时显示规范网址、ICP 备案号、凭证编号和校验摘要，并明确“付款凭证不替代发票”。图片不得写成第三方在线付款或纸质合同凭证，也不得包含恢复令牌、企业银行完整账号或完整敏感资料。

## 4. 游骑兵合同

公开职业档案只展示：

- 公开名称；
- 一个顾问身份；
- 可选的个人签名（顾问本人的一句话表达，最长 120 个字符）；
- 可选的本人授权公开头像；
- 一句话介绍；
- 专长标签；
- 可选公开资质；
- 经本人授权的职业联系方式；
- 核验日期与资料更新时间。

用户直接联系顾问。Vault2077 不参与后续咨询、定价、付款、交付或争议处理，也不把统一工作人员联系方式放到游骑兵卡片上。页面必须持续显示独立关系声明。

头像只能由受保护后台上传。服务端解码并生成 320×320 与 800×800 两份 WebP，去除原图元数据后保存到 ADR-0016 规定的媒体存储；目录只保存不可变对象引用。后台不接受任意第三方图片 URL，未上传头像时继续使用非人物化占位肖像。

## 5. 页面与路由

- `/opc`：唯一公开工作台，通过 `view=infrastructure|specialties|rangers` 恢复三个一级视图，不建立重复分类页面。
- 基础设施与专项服务不设置独立详情页；用户在 `/opc` 工作台内直接展开具体服务。
- 服务使用稳定 slug 写入工作台查询参数（例如 `/opc?view=infrastructure&service=<slug>`），名称修改不影响入口；查询参数只负责恢复选中状态，不复制一套详情页面。
- 游骑兵公开档案使用稳定的 `/opc/rangers/[slug]` 个人详情路由，详情 URL 不随公开名称修改而变化。

顾问详情页的首屏遵循“识别人 → 看见人 → 听见其判断 → 核验档案”的顺序。姓名区只包含登记信息、公开姓名与一句话介绍，头像与姓名并列；如填写个人签名，必须原文放在主画面之后、核验登记栏之前的独立自述签发带中，并以贯穿姓名区和头像区的横向细线结构承载，不使用卡片、色块或引号装饰，也不得重新塞回姓名区。宽屏有签名时，自述签发带与其下核验登记栏使用等高轨道，标签、签名原文和登记内容均在各自栏内垂直居中；窄屏恢复由内容决定高度。签名最长 120 个字符，宽屏使用横向长行，窄屏在标签下自然换行并允许页面增高；任何连续字符都必须强制断行，不得侵入头像或造成横向滚动。留空时整条签发带不渲染。

桌面端和移动端共用同一工作台信息结构；移动端只改变分栏排列，不以独立详情页作为兼容方案。

游骑兵姓名书架的书脊只通过悬停或键盘聚焦自动展开，不承担点击导航；真实顾问展开后的整幅头像必须是指向稳定 `/opc/rangers/[slug]` 的链接，不另加详情按钮。布局宽度先切换到最终状态，再用 FLIP 合成变换完成约 1.25 秒展开与较短收回，禁止逐帧动画化 `flex-grow`、网格列或宽度；系统请求减少动效时直接显示最终布局。窄屏收拢状态下每位真实顾问仍保留至少 30px 可见书脊，不能被压成无法辨认的细线。

## 6. 数据与运营

- OPC 是全站唯一允许后台直接维护公开目录正文的产品频道；可编辑对象只包括基础设施、专项服务和游骑兵公开档案。Vault 资讯、来源事实、SiC 内容与平台榜、Frontier 排名继续由各自自动管线产生，后台不得用同一编辑接口改写。
- 后台编辑草稿，公开页面只读取最近一次已发布快照。保存草稿不改变前台；发布要求二次确认、乐观版本检查、字段完整性校验和不可变审计记录。
- 后台支持新增、删除、排序和编辑具体服务、游骑兵档案与顾问身份。一级入口、专项专业领域和基础设施浏览分组仍不得由请求任意增加；顾问身份只能作为同一 OPC 目录草稿中的稳定 ID／公开名称记录维护，不能扩展成任意页面栏目。
- 已发布服务修订不可静默覆盖；新订单在服务器创建时绑定当时的已发布修订，修订不作为用户展示字段。
- 新订单创建时保存服务类型、slug、编号、名称、修订、公开价格、范围、周期、成果、固定金额、在线协议正文/版本/SHA-256/确认时间、敏感信息单独同意版本/时间、付款资料修订、企业账户快照、PDF 与二维码 SHA-256，以及加密姓名、手机号、身份证号码和通知邮箱；银行核验后保存唯一流水号、加密付款户名、入账时间和核验时间。后续目录、协议、账户或二维码修改不改变历史订单。
- 企业账户、协议 PDF 与二维码必须作为同一修订原子发布到 PostgreSQL；VPS 文件只是替换暂存输入，现有头像和合同 OSS 均不存放本资料。资产响应不得缓存，PDF 以内联响应支持弹窗预览，并由同源下载入口显式下载；仅协议 PDF 精确路径允许本站 iframe，二维码和其他页面继续禁止嵌入。
- 同一付款资料修订不得覆盖不同内容；资产 URL 的 SHA-256 必须与服务器当前修订匹配，旧页面不得混用新 PDF 或二维码。用户生成订单后和页面刷新后都能从当前浏览器进入付款状态/凭证页。
- 创建线下订单时在同一事务写入用户与负责人两个 `order_created` outbox 事件；首次银行到账确认时生成唯一不可变付款凭证快照、凭证编号与 SHA-256，并写入用户与负责人两个 `payment_confirmed` outbox 事件。每个事件身份包含类型和受众，重复请求或重复流水不得生成第二份同受众事件或第二份凭证。
- 银行流水号在保存、判重和审计指纹前统一规范化；尚未确认到账的银行订单可由最近五分钟再认证的后台取消，取消记录与审计原子提交并进入 90 天联系人清理。
- 付款／委托方和订单联系方式使用数据密钥环加密；通知 worker 只在领取用户事件时解密收件邮箱，公开状态和普通后台摘要不返回明文邮箱。未付款取消订单满 90 天清除联系人；已付款订单完成或退款满 24 个月后清除非合同联系方式。
- 退款申请原因使用数据密钥环加密，只在最近五分钟再认证的订单 dossier 中解密。普通联系信息导出不包含身份证号码；dossier 只显示身份证遮罩。`refund_requested` 邮件只含脱敏订单摘要和管理后台链接。
- 新订单 `待付款 → 已到账可履约` 只由最近五分钟再认证的后台银行证据核验和服务端强制的逐项核对确认驱动；`已到账可履约 → 已完成` 由后台交付结论驱动。线下退款尚未形成自动状态机，不能以普通状态修改伪造退款完成。退役在线渠道仅保留中性只读历史凭证，不提供验真、查询、关单或原渠道退款操作。
- 每次发布保存带修订号和时间的完整目录快照；删除只影响新公开目录，历史发布快照继续可追溯。
- 下架服务不接受新订单，但历史订单仍可追溯。
- 顾问资料必须有授权、核验和撤回流程；撤回后公开页面停止展示。
- 价格、法律声明、真实顾问资料与收款方式属于上线前业务输入，不能用演示数据冒充。
- 公开页面不展示内部备注、私人联系方式、适用性判断或运营状态。

## 7. 状态与验收

- 三入口在桌面与移动端均可直接到达。
- 首版目录以七项基础设施、十四项专项服务和十个初始顾问身份初始化；后续服务、档案和顾问身份增减必须来自有审计记录的 OPC 菜单发布，专项服务仍只用六个专业领域。
- 服务卡和顾问卡的责任主体、联系对象和行动文案不会混淆。
- 未登录用户不能读取草稿；保存草稿不改变前台，版本冲突不会覆盖他人修改，字段不完整或仍为占位内容时不能发布。
- 空列表、已下架、资料过期、联系入口不可用均有明确状态。
- 标准宽度 `360 / 768 / 1280 / 1440` 无横向溢出，筛选可键盘操作。
- 页面不出现旧六分类、购物车或游骑兵统一客服入口；标准服务详情必须提供联系方式登记与付款入口。
- 付款方式只显示线下对公转账，不展示已退役在线支付入口、按钮或恢复承诺。
- 企业账户、协议弹窗/PDF 下载和联系人二维码在转账前同页可见；二维码没有联系人介绍，用户可先扫码再决定转账。
- 用户提交前可以完整查看和下载协议，并填写用于接收订单与到账通知的有效邮箱；提交后生成唯一订单号/付款附言且不跳转第三方收银台，到账只由后台银行实际入账证据推进。
- 付款单生成后页面直接提供付款状态与凭证入口；同一浏览器刷新后仍可进入最近订单状态页。
- 页脚退款入口可在原下单浏览器安全查询订单并提交幂等申请；错误凭证不能枚举订单，申请成功不被表述为退款完成。
- 银行核验后用户可以查看并下载付款凭证图片，服务、金额、双方主体、网址和 ICP 备案号与服务器锁定快照一致，图片不泄露恢复凭证、付款户名或完整联系信息。
- 后台订单 dossier 贯通服务/协议、付款资料修订、企业账户快照、付款方、银行流水、凭证、四类通知状态和审计；完整联系信息需要最近五分钟再认证。用户邮件只链接公开订单状态页，负责人邮件只提供脱敏摘要和后台安全链接。
