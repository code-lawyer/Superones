# ADR-0024：SiC 逐条发布存储与非破坏性来源更新

## 背景

SiC 采集原始批次已可靠进入 PostgreSQL inbox，但公开内容曾只保存在一个 `sic-content` JSONB 状态文档中。增量批次把合法 `empty` 报告误当成权威空快照，整来源替换为零条；重新部署后 worker 处理新批次，使先前已发布的课程、档案和播客从该状态文档消失。原始批次仍在 RDS，但公开读取只看当前发布态，因此前端无法自行恢复。

## 决定

1. `vault2077_acquisition_inbox` 继续保存受限期限内的原始、已签名采集事实；它不是公开查询模型，公开页面不得读取或临时处理 inbox。
2. SiC 经境内编辑验证的条目规范化写入 `vault2077_sic_published_items`。每条记录有稳定内容身份、来源、内容组、来源快照、当前激活状态和发布／退出时间；退出公开集合只改为 inactive，不物理删除恢复证据。
3. 来源报告只有 `success` 表示一个可权威替换的完整来源集合；`partial` 只合并合格条目，`empty` 与 `failure` 都保留上一成功发布集合。来源退出 approved 注册表是独立的显式退役命令，可以停用该来源。
4. 迁移期继续在同一 PostgreSQL 事务内双写旧 `sic-content` 状态文档，保证上一 release 可回滚读取。规范化元数据保存旧文档公开投影摘要；摘要不一致时当前 release 立即回退读取旧文档，避免回滚期间的旧版写入被较旧规范化投影遮盖。
5. 页面使用的“快照 ID”只是一次分页读取的一致性清单，不是内容唯一存储，也不改变逐条发布表作为当前 SiC 公开事实源的地位。
6. 恢复命令默认 dry-run：校验 inbox 正文摘要，从最近一次已处理 bootstrap 起按时间重放来源语义；历史同轮物理分片先合并成一个逻辑运行，再按同来源最差完整性和合计条目数生成唯一报告，避免任一 `success` 分片误触发整来源替换或诊断计数重复。命令报告当前发布数和原始预计数；写入模式必须先在临时文件库完成境内编辑、通过内容组非空护栏，再以当前投影摘要作乐观锁，将完整候选一次性事务写入旧文档与规范化表。

## 后果

- 部署必须先备份，再运行迁移；迁移后但尚未初始化时应用仍从旧文档读取，不产生空窗口。Web/health 前必须显式运行幂等初始化命令并留存摘要与计数对齐证据，不能依赖后续 worker 写入触发。
- 空增量、部分编辑、完整成功、来源退役和上一 release 回滚都必须有自动化合同测试。
- 当前 acquisition v2 没有来源分片完成标志，同一 SiC 来源的权威集合不得跨批拆分；超过单批上限时失败关闭。未来需要超大来源分片时必须先升级带完整性清单的合同。
- inbox 的 30 天成功批次保留期同时限定无需 PITR 的应用级重放窗口；超过窗口的恢复依赖 RDS 时间点恢复或独立受审计归档。
- 管理域应报告来源最近成功、空／失败和发布计数；公开页面仍不展示运维诊断。
