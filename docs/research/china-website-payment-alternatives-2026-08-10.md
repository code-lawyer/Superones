# 中国大陆企业网站支付替代方案（2026-08-10）

## 1. 结论

本文研究 Vault2077 以中国大陆公司主体、人民币价格向国内用户销售专业服务时，支付宝之外的收款方案。本文只使用支付平台、收单机构和项目代码的一手资料；它是决策证据，不改变产品规格、订单状态或生产开关。

推荐顺序不是“谁审核宽松”，而是：

1. **企业对公银行转账，作为临时受控收款方案。** 使用网站经营公司同名账户，不再出现个人收款方；无需等待另一家互联网支付产品开通。但付款确认、对账和退款主要依赖人工与银行流水，不是即时网页支付体验。
2. **微信支付 Native，作为正式在线支付首选替代。** 微信官方明确把 Native 定义为 PC 端网页浏览器收款，二维码下单、服务器通知、主动查询和原路退款能力与现有支付宝闭环最接近。[微信支付：Native 产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4012791874)、[微信支付：订单退款业务示例](https://pay.wechatpay.cn/doc/v3/merchant/4015217336)
3. **银联在线网关/企业网银支付，作为银行卡覆盖的第二在线通道。** 银联官方提供 PC 在线网关、异步通知、查询、退货/退款和对账；企业网银支付尤其适合企业付款人，但直联入网和证书接口的实施、联调成本高于微信 Native。[中国银联产品商店](https://open.unionpay.com/ajweb/productStore)、[企业网银支付（商户版）](https://open.unionpay.com/tjweb/acproduct/list?apiservId=452)、[商户入网测试接入指南](https://open.unionpay.com/tjweb/support/doc/online/7/253)
4. **持牌收单机构/聚合支付，作为后续多通道方案。** 可用一个服务商聚合钱包和银行卡能力，但仍需商户入网、场景审核和上游渠道权限；它不是绕开支付宝或微信审核的办法。银联商务官方平台明确先入网成为商户，再申请服务、取得接口权限；其能力支持 PC、电子钱包及银行账户。[银联商务天满服务平台](https://saas.chinaums.com/saas-web/)、[银联商务综合支付服务](https://www.chinaums.com/shums/shfw/)

当前不应推荐个人收款码、个人账户代收、借用他人商户号或虚构经营类目。这些方式会重复当前“网站经营主体为公司、实际收款方为个人”的风险，也破坏订单凭证、退款和财务归属。

## 2. 方案对比

| --- | --- | --- | --- | --- | --- |
| 企业对公转账 | 可在付款页展示公司户名、开户行、账号和唯一附言；不是即时收银台 | 银行开户时已核验企业主体；不等于银行替网站经营内容背书。是否需要额外网银或银企直联审核取决于开户行，当前没有官方统一承诺 | 普通转账没有统一的网页支付回调或通用原路退款 API；依赖流水核对，退款由公司账户另行转出 | **中等**：新增银行转账支付类型、唯一附言、后台双人核验和退款证据；不得依据用户截图自动标记到账 | 最快的受控临时方案，体验和自动化较弱 |
| 微信 Native | **最适合 PC**；官方定义即 PC 浏览器展示动态二维码，用户微信扫码 | 企业可申请，但必须提交营业执照、法人和对公账户等资料并完成审核、签约和场景绑定；平台会审核经营场景，不能假定比支付宝宽松。[PC 网站接入指引](https://pay.wechatpay.cn/static/applyment_guide/applyment_detail_website.shtml) | API v3 下单、支付通知、主动查单、关单、退款、退款通知均可形成服务器证据闭环 | **中高**：抽象支付提供方；新增 mchid/appid、证书/公钥、通知解密验签、查单、关单和退款适配 | 正式替代首选；先解决公司主体及网站风险展示问题再申请 |
| 微信 H5 | 只适合手机外部浏览器，不适合作为 PC 主通道 | 官方要求企业等主体及已认证应用；申请时支付一级域名必须公网可访问并展示具体经营内容，还会核对 ICP 主办单位、商户主体、合作关系及特殊资质。[H5 产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4012791832)、[H5 权限申请](https://pay.wechatpay.cn/doc/v3/merchant/4012791841) | 与微信支付 API v3 共用服务器通知、查单和退款体系 | 在 Native 适配基础上增加移动端跳转与浏览器兼容，**中等增量** | 未来移动浏览器补充，不替代 PC Native |
| 微信 JSAPI | 仅微信客户端内网页；不是普通 PC 浏览器支付 | 需要已认证服务号等应用、商户号与 AppID 绑定、支付目录和授权域名；同样存在主体和场景审核。[JSAPI 产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4012062524)、[JSAPI 接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4012164506) | 通知、查单、退款能力完整 | 还需公众号、openid 和微信内浏览器流程，**高于 Native** | 仅在运营公众号流量时补充，不作为当前首选 |
| 银联在线网关/云闪付线上能力 | 银联网关明确属于 PC 在线收款；云闪付 APP 支付偏移动应用，PC 网站应优先选择在线网关，而不是把云闪付 APP 控件当 PC 方案 | 银联公开流程是“入网申请与审核 → 开发联调测试 → 投产上线”；直联指引还要求提交机构资质并检查准入。无官方证据支持其会忽略网站或经营风险。[加入银联网络](https://open.unionpay.com/ajweb/product/detail?id=1)、[直联商户接入指引](https://open.unionpay.com/upload/download/%E4%B8%AD%E5%9B%BD%E9%93%B6%E8%81%94%E7%BD%91%E9%93%B6%E6%94%AF%E4%BB%98%E4%B8%9A%E5%8A%A1%E7%9B%B4%E8%81%94%E5%95%86%E6%88%B7%E6%8E%A5%E5%85%A5%E6%8C%87%E5%BC%95.1.0.pdf) | 官方全渠道平台提供后台通知、状态查询、退货/退款和对账；企业网银产品可退款回原企业账户 | **高**：证书、报文、前后台通知、查询、退货、对账文件及投产联调 | 可靠的第二在线通道，适合银行卡和 B2B 客户 |
| 持牌收单/聚合支付 | 视服务商产品，可聚合 PC、手机、钱包和银行卡 | 仍需成为服务商的特约商户并取得具体接口和上游通道权限；具体资料、费率和审核时限必须以候选机构书面入网清单为准 | 通常有下单、通知、查询、退款和对账，但能力、退款时限、资金结算主体均需逐项验收 | **中高**：单接口可能更省开发，但增加服务商依赖、子商户号、结算和通知签名差异 | 适合后续多通道，不作为规避当前审核的捷径 |

## 3. 为什么微信也可能遇到类似审核

微信支付不是“换个平台就不看网站”。官方 PC 网站入驻指引要求企业提供营业执照、法人证件和对公银行账户，审核通过后签约并绑定场景。[PC 网站接入指引](https://pay.wechatpay.cn/static/applyment_guide/applyment_detail_website.shtml) 微信支付的经营场景管理文档还说明，经营场景用于开通收付款功能，平台会定期检查场景真实性；场景资料需要让平台辨识主营业务。[经营场景管理](https://pay.wechatpay.cn/doc/v3/merchant/4017312501)

H5 的公开申请规则更直接：支付域名必须公网可访问并展示具体经营内容，ICP 主办单位与商户主体不一致时只接受列明的真实合作关系，特殊经营内容还需补充资质。[H5 权限申请](https://pay.wechatpay.cn/doc/v3/merchant/4012791841) 因而，支付宝提示的“网站风险较高”若源于域名信誉、经营内容不清晰或类目/资质问题，微信或收单机构也可能作出类似风险判断；换渠道不能代替修复网站风险和主体一致性。

## 4. 与现有订单状态机的关系

当前系统不是通用支付层：订单持久化和校验直接绑定支付宝 `appId`、`sellerId/PID`、支付宝交易号、支付宝通道与退款证据；付款通知、主动查询、关单、付款凭证和全额原路退款也使用支付宝专用类型和错误语义。系统规格明确要求核对订单绑定的 APPID、PID、订单号、金额和状态。

因此不能只把环境变量中的支付宝密钥换成微信或银联参数。正式增加在线通道至少需要：

1. 为订单保存不可变的 `paymentProvider`、提供方商户/应用标识、提供方订单号和交易号；旧订单继续路由到原提供方凭证。
2. 抽象“创建支付会话、通知验签、主动查询、关闭、退款、退款查询”能力，但保留当前服务器证据核验、固定金额、幂等请求号和终态门禁。
3. 把付款凭证和后台 dossier 的字段从“支付宝专用”提升为提供方中立，同时完整保留原始提供方摘要和审计证据。
4. 多通道期间不能用当前配置去查询或退款旧通道订单；必须按订单绑定的提供方和商户身份路由。

当前唯一真实支付宝测试单已经全额退款，公开支付入口保持关闭，因此现在切换或增加提供方比产生真实未完结订单后再迁移安全得多。

### 分方案改造判断

- **微信 Native：中高。** 对现有动态支付会话、异步通知、主动查询、关单和原路退款模型匹配最好，主要工作是支付提供方抽象和微信 API v3 安全实现。
- **企业对公转账：中等代码量、高运营量。** 不需要外部支付 SDK，但必须新增“等待银行到账证据”的人工核验路径。用户上传回单或截图只能作为线索，不能作为到账证据；退款也不是支付通道自动原路退款。
- **银联直联：高。** 状态模型匹配，但证书报文、前后台通知、状态查询、退货及对账联调面更宽。
- **聚合支付：中高。** API 面可能较小，但必须验证它是否提供主动查单、稳定退款请求号、退款查询、签名通知和企业同名结算；缺一项就不能复用当前安全门禁。

## 5. 建议执行顺序

1. 继续保持现有公开支付入口关闭，不再使用个人支付宝收款。
2. 若业务必须先开始，设计公司对公转账的受控人工流程；只有银行已入账证据才能将订单推进到已付款状态。
3. 同时以网站经营公司申请微信支付商户号和 **Native 支付**，提交真实服务页、价格、交付、退款规则、公司主体和备案材料；不承诺审核结果或时限。
4. 只有微信企业收款方、真实小额支付、服务器通知、主动查询、付款凭证、关单及全额退款全部通过后，才开放在线支付。
5. 银联在线或持牌聚合收单作为第二阶段评估；候选机构必须书面确认 PC 网页产品、专业服务类目、结算主体、费率、保证金、退款期限、API/回调、对账和退出条款。

## 6. 仍需向候选机构确认的未知项

公开官方页面不足以确认 Vault2077 所属专业服务细分类目的实际费率、结算周期、保证金、审核时限或必然准入结果。以下信息不能推测：

- 微信 Native 对本次具体服务类目要求的补充资质及最终费率；
- 银联是接受商户直联，还是要求通过指定收单机构入网；
- 聚合机构是否真正开放 PC 网页收款、主动查询、全额原路退款和退款查询；
- 各机构是否同样命中当前域名风险库，以及具体申诉入口。

这些项目应在选择候选机构后，以后台申请页或机构盖章/签署的入网清单、报价和技术接口文件为准。
