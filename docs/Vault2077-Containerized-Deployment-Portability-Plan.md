# Vault2077 容器化与跨服务器重布置远期目标

## 1. 文档状态

本文件记录项目负责人确认的远期开发目标：在不改变公开域名和产品信任边界的前提下，将境内应用运行时容器化，并建立可演练、可验证、可回滚的跨服务器与跨云重布置能力。

这不是当前生产部署合同，也不表示仓库已经支持 Docker 发布。当前有效方式仍是 GitHub Actions 构建 Linux `tar.gz` 发布包，在目标服务器解压后由 Nginx、systemd、journald 和 logrotate 运行。开始实现本目标前必须接受相应 ADR，并同步修改系统交付规格、上线清单、部署手册、运行手册和项目长期记忆。

## 2. 目标

- 从负责人批准的 commit 可重复构建一个不可变、可核验 digest 的 Linux 生产镜像。
- Web、采集 inbox worker、health、Frontier tick、游骑兵媒体清理和 OPC 订单维护使用同一个镜像，通过不同命令运行。
- 新服务器无需在生产机编译项目或安装项目专用 Node 依赖，只需准备受支持的容器运行时、反向代理、受控配置和外部资源网络。
- 在 `superones.top`、`admin.superones.top` 和 `media.superones.top` 不变时，可把计算节点从一台服务器迁到另一台服务器，或从一家中国大陆云厂商迁到另一家。
- PostgreSQL 资源需要同时迁移时，具备同大版本全量、增量追平、短时停写割接、一致性验证和明确回滚点。
- Passkey、加密业务数据、不可变审计、支付状态、采集 inbox 和公开内容在重布置后保持可读、可验证和连续。

## 3. 目标拓扑

第一阶段采用“应用容器化、宿主机入口与调度保留”的渐进方案：

```text
公网 :443
   |
宿主机 Nginx / TLS / 安全头 / 限流
   |
127.0.0.1:3000（宿主机只绑定回环）
   |
Vault2077 Web 容器（容器内监听 0.0.0.0:3000）
   |
   +-- 外部 PostgreSQL（生产事实源）
   +-- 外部对象存储（公开媒体与未来私有合同相互隔离）
   +-- 支付、邮件、GitHub 与编辑提供方

宿主机 systemd timers
   |
   +-- 使用同一镜像运行一次性 worker / health / Frontier / OPC 命令
```

首阶段不要求把 Nginx、证书续期、systemd timers、journald 或 logrotate 一并放入容器。保留这些已经具备安全门禁和失败告警的宿主机能力，可以把改造 seam 收敛在应用运行时，同时减少一次性替换整个生产拓扑的风险。只有完成目标环境演练后，才评估是否进一步容器化入口和调度。

## 4. 容器交付合同

- 镜像至少支持当前生产架构 `linux/amd64`；增加 `linux/arm64` 前必须单独验证 Node、Sharp、构建产物和全部 E2E。
- 构建使用多阶段 Dockerfile，固定 Node 主版本、锁文件和生产依赖；生产镜像以非 root 用户运行。
- 镜像不包含 `.env*`、生产环境文件、密钥、恢复码、数据库备份、本地预览数据、测试输出或 Git 凭证。
- 生产配置仍由 root-only 文件或等价的受控秘密注入机制在运行时提供；秘密不得作为 build arg、镜像层、Compose 文件正文或 CI artifact 写入。
- Web 容器内部监听 `0.0.0.0:3000`，但宿主机端口只允许映射到 `127.0.0.1:3000`；Node 端口、内部 health 和处理入口不得直接暴露公网。
- PostgreSQL 和对象存储继续作为容器外的生产适配器。生产不得挂载 `data/*.json` 作为事实源，也不得在数据库失败时回退文件预览。
- Next.js 必需的临时目录和缓存使用最小可写挂载或临时卷；任何容器本地文件都不得成为业务恢复依赖。
- 数据库迁移作为显式的一次性发布步骤运行，不隐藏在可能并发启动的多个 Web 容器 entrypoint 中。
- CI 记录 commit、镜像标签、镜像 digest、目标平台和构建证据；“推送镜像”不能描述为“已经部署”。
- 回滚以已验证的旧镜像 digest 为单位，至少保留当前和两个最近可回滚版本。

## 5. 不可破坏的运行边界

容器化不能改变以下现有合同：

- 公开主机只精确开放已批准的两个内部跨境接口；后台、health、处理入口、数据库和 Node 端口仍不得从公网或源站 IP 绕过。
- 生产后台继续只接受 `https://admin.superones.top` 上固定 owner 的原生 Passkey，不恢复共享密码、OIDC、Basic Auth 或客户端身份断言。
- Passkey RP ID 继续由不变的管理域名派生；换服务器、重新签发相同域名的 TLS 证书或更换数据库地址不能要求用户改用新域名。
- PostgreSQL 继续是公开内容、业务状态、Passkey、安全审计、会话和任务状态的唯一生产事实源。
- 境外 GitHub Actions 继续只采集公开数据并投递签名批次；境内独立 worker 才调用编辑模型和写入生产状态。
- 数据 keyring、OPC 恢复令牌 keyring、管理员会话秘密、管线签名和第三方凭证必须从负责人可恢复的安全保管处注入；跨服务器搬迁不得趁机无计划轮换或丢弃旧 key ID。

## 6. 跨服务器重布置合同

### 6.1 计算节点迁移

1. 在新服务器安装并固定容器运行时与 Compose 能力，配置防火墙、时间同步、磁盘、日志和告警。
2. 拉取负责人批准的不可变镜像 digest；不得在生产服务器从源码临时构建。
3. 通过受控渠道恢复生产配置，只核对字段状态、权限和指纹，不打印秘密值。
4. 在不切 DNS 的情况下运行 `deploy:check`、编辑提供方探针、数据库连接、health 和浏览器主流程验证。
5. 为新服务器准备相同公开与管理域名的有效 TLS；Passkey 验收必须发生在真实 `admin.superones.top` 来源，可使用受控 hosts/DNS override 预验收。
6. 切换期间保证只有一组 timers 执行业务写任务。新旧 Web 可以短时共同读取同一生产数据库，但不得分别写入两个不同数据库。
7. DNS 切流前确定旧节点的维护、转发或停写方式；DNS 传播期间旧节点不得继续向已经退出的旧数据库写入。
8. 新节点通过 health、四通道、后台、支付回调和业务验收后再启用 timers；旧节点保留到观察期结束后再释放。

### 6.2 PostgreSQL 同时跨云迁移

- 源和目标优先使用相同 PostgreSQL 大版本；云厂商迁移与数据库大版本升级不得合并为一次变更。
- 首选目标厂商支持的“结构 + 全量 + 增量”逻辑迁移能力，或经过演练的 PostgreSQL 原生等价方案；`pg_dump`/`pg_restore` 作为演练、备份和允许较长停机时的备选。
- 迁移前建立真实备份/恢复点，验证目标实例 SSL、备份、日志备份/PITR、删除保护、容量、字符集、时区、collation、角色、owner、扩展和网络白名单。
- 跨云传输优先使用 VPN、专线或等价受控网络；必须临时使用公网时，只放行迁移任务的精确地址、启用 TLS、使用专用最小权限账号，并在完成后撤销入口和账号。
- 全量和增量阶段冻结 DDL，监控复制槽、WAL、磁盘、源/目标负载、迁移延迟和长事务。
- 正式割接必须先停止旧 Web 写入、worker 和全部 timers，确认没有业务写会话，等待增量差距与延迟归零并保持稳定，再完成迁移任务。
- 目标库至少核验迁移表及 checksum、各表行数、状态文档 namespace/version/哈希、审计 ID、Identity/sequence、不可变触发器、Passkey 数量、订单状态和 inbox 状态。
- 完成迁移后在目标库运行幂等迁移门禁、PostgreSQL 集成测试和应用 health，再开放新 Web；只有业务验收通过后才恢复 timers 和写功能。
- 旧数据库在观察期内保持受控只读和可恢复，不在割接成功后立即删除。

### 6.3 回滚点

- 目标数据库尚未接收任何新业务写入时，可以停止新节点并恢复旧节点与旧数据库。
- 目标数据库一旦接收新订单、支付、Passkey、审计、采集或后台写入，就不得直接把应用指回已经落后的旧数据库。
- 进入上述写入提交点后，普通应用故障应回滚旧镜像但继续使用目标数据库；若必须回迁数据库，先重新停写，并执行反向增量同步或经审计的数据补偿。
- 生产切换方案必须明确记录“最后可无损回退时间”、切换后的数据负责人和回迁方法，不能把 DNS 回切误当作数据库回滚。

## 7. 中国大陆跨云接入要求

如果公开入口从一家中国大陆云厂商迁到另一家，在公共 DNS 切换前完成目标接入商要求的 ICP 接入备案、域名校验和相关前置手续。原备案号和域名不变不代表新接入商已经完成接入备案；迁移窗口不得以未完成接入备案的目标服务器承接正式流量。

备案接入、DNS、TLS、数据库迁移和应用容器切换是四条独立工作流。它们可以在同一 Go/No-Go 窗口汇合，但不得互相替代。

## 8. 分阶段开发路线

### 阶段 A：决策与基线

- 接受容器化部署 ADR，确认首阶段保留宿主机 Nginx/systemd。
- 记录当前 tar.gz 发布的性能、RSS、启动时间、health、日志和回滚基线。
- 明确镜像仓库、保留期、供应链扫描、签名/证明、目标平台和失败告警。

### 阶段 B：镜像与本地验证

- 增加生产 Dockerfile、`.dockerignore`、Compose 配置和容器运行说明。
- 在 Linux CI 构建镜像，验证 Sharp、Next.js、Node 24 和生产依赖。
- 覆盖 Web 与全部一次性命令，运行文档、Lint、类型、Node/Python 测试、构建和两套 E2E。

### 阶段 C：部署适配器与 CI

- 增加以镜像 digest 为输入的安装、检查、启动、停止和回滚流程。
- 将现有 systemd oneshot/timer 映射到同一镜像中的命令，并保留失败告警语义。
- 让构建 workflow 产出可核验镜像；仍不增加未经批准的自动生产部署。

### 阶段 D：第二服务器演练

- 在不改变生产数据库和公开 DNS 的情况下，从空白 Linux 主机重建应用节点。
- 验证相同管理域名下的 Passkey、公开/后台 Host 边界、源站 IP 拒绝、health、四通道和定时任务互斥。
- 完成一次旧镜像 digest 回滚和一次服务器整体重建演练。

### 阶段 E：数据库迁移演练

- 恢复生产备份或使用脱敏等价数据，在隔离目标 PostgreSQL 上完成全量、增量、停写、割接和回滚演练。
- 验证身份、序列、触发器、JSONB 状态、加密数据、审计不可变性和迁移 checksum。
- 以演练证据确认目标 RPO、RTO、最大停写时间和写入提交点。

### 阶段 F：生产采用

- 更新系统交付规格、上线清单、部署/恢复手册和项目记忆，将 Docker 从远期目标提升为当前受支持部署方式。
- 按备份、门禁、迁移、health、业务验收、timers 和 DNS 顺序执行生产切换。
- 观察期完成并具备可恢复证据后，才退役旧发布方式、旧服务器或旧数据库。

## 9. 验收标准

- 一台空白、受支持的 Linux x86_64 主机能够仅凭固定镜像 digest、仓库内部署配置和安全注入的环境文件恢复应用，不在生产机编译源码。
- 镜像内不含秘密和业务数据，以非 root 用户运行，宿主机只在回环暴露 Node 端口。
- Web 与全部生产一次性任务使用同一 commit/digest，且保留当前超时、资源上限、互斥和告警语义。
- 从备份恢复或增量迁移后的 PostgreSQL 能通过迁移 checksum、集成测试、health、Passkey、审计、订单和四通道验证。
- 相同 `admin.superones.top` 上的既有 Passkey 可继续使用；即使应用会话自然失效，也无需因换服务器重新注册凭证。
- 演练证明 DNS 传播期间不会出现新旧数据库双写；只有一组生产 timers 处于启用状态。
- 演练分别证明应用镜像回滚、计算节点回滚和数据库回迁的不同门禁，不把三者混为一个“回滚”。
- 中国大陆跨接入商迁移已在切流前完成目标接入备案，公开站与管理站不会因未接入而被阻断。
- Docker 采用后，当前文档中所有“tar.gz + `/srv/vault2077/releases` + 宿主机 npm”表述已同步修订或明确标为兼容路径，不保留互相冲突的当前运行合同。

## 10. 非目标

- 本计划不要求 Kubernetes、多云同时写、数据库双主、跨云自动故障转移或无人值守 DNS 切换。
- 本计划不把 PostgreSQL 放入同一生产 Compose 作为长期事实源。
- 本计划不授权自动执行真实资金、Passkey 实体注册、RPO/RTO 降级、接入备案提交、DNS 切流或最终 Go/No-Go。
- 本计划不改变当前境外采集与境内编辑的信任域，也不把生产秘密复制到 GitHub Actions。

## 11. 实施触发条件

本目标属于远期能力，不阻塞当前首发。满足以下任一条件时，应把阶段 A 提升为正式开发计划：

- 已确定需要更换生产服务器、地域或云厂商；
- 当前宿主机运行时、发布包或回滚流程成为明确运维瓶颈；
- 需要在隔离服务器上建立可重复的灾难恢复节点；
- 负责人为该目标安排独立开发与演练窗口。
